# 游戏更新与老玩家存档兼容

2026-10-28 用户明确要求：**每次更新必须保留老玩家记录，平滑迁移。存档兼容属于强制发布门禁，不是可选优化。** 所有工作区游戏、执行者与每日自动化都遵守本规范；不能为实现新玩法、改名、重做 UI 或通过测试而清空既有进度。

## 必须保留什么

逐游戏登记实际存在的资产：主线/关卡/经营进度，金币等资源与付费/广告权益，角色/车辆/物品解锁、收藏与图鉴，成就、历史最高分/最佳用时、各赛道纪录，任务、设置和用户已作的选择。多人房间瞬态、过期活动或新旧玩法确实无法一一对应的内容要单列，先定义对玩家公平且不丢价值的转换方案，不能静默归零或把旧赛道分数冒充新赛道。

软件版本与存档 schema 版本分开。通常保留稳定的存储 key、数据库名、账户/云存档命名空间；仅因发布 `1.x→2.x` 不得换 key 或重建库。不以“最新玩法”为名忽略旧key，也不只在内存读到旧值后忘记持久化。

## 迁移实现底线

1. 读取旧存档前保留原始数据，在原key/原数据库下保持可恢复副本。解析或迁移异常时不向旧位置写默认新档；提示重试/恢复并保留证据。不能在catch、版本不匹配、缺字段、网络失败或权限错误时直接 `clear()` / `removeItem()` / 删除数据库。
2. 明确支持的历史schema与迁移链，逐步补字段、重命名和转换，校验有限数字、边界、集合和旧赛道归属。新存档先完成转换与校验，再原子提交或采用可恢复的提交标记；发生中断可重试。不得先删旧档再写新档。
3. 迁移幂等：再次加载、刷新、前后台切换不会再次发币、重复消耗、重复补偿、累计分数或覆盖更好的纪录。未知的未来schema保留原数据并进入可恢复的不兼容状态，不降级重置。
4. 本地与云端/平台存档分别核对。云读失败不能用空档覆盖远端；多端/冲突按明确revision/时间/资产策略合并，不凭“字段更多”或本机当前时间覆盖较新进度。没有云存档的项目不能宣称提供跨设备恢复。
5. H5来源隔离要单独查：`localStorage` / IndexedDB 属于 origin，域名、scheme、端口、平台 App ID、WebView容器、账户或命名空间变化都可能让旧记录不可见。不同origin无法仅靠新页面读取旧本地数据；需要平台稳定来源、受支持桥接/云存档或用户可恢复导入方案。清缓存、重装、游客切号也要与代码迁移失败区分，不编造“更新自动迁移成功”。
6. 回滚策略明确：保留旧存档副本、迁移标记与读写兼容说明。只能回滚到懂得当前schema或能安全恢复旧副本的版本；不能因代码可回滚就宣称玩家记录可回滚。

## 每次发行的必检矩阵

使用**实际上线的上一版本**及仍支持的历史schema，连同候选最终ZIP/commit建立证据。至少覆盖新玩家空档、浅层旧档、深层/大量解锁旧档、上次版本旧档、跨多版本旧档、缺字段、损坏/截断、未知未来schema、存储写入失败、迁移中断/重试和重复加载。只测新安装不能作为更新验收。

| 检查 | 必须确认的结果 |
| --- | --- |
| 旧版建立进度 → 候选版 | 同一账号、App ID、存储命名空间及来源下逐项核对，资源/进度/解锁/纪录不丢 |
| 刷新/强退重开/前后台 | 迁移已持久化，结果一致；没有重复奖励或重复消耗 |
| 读取/校验/写入失败 | 原数据未被默认新档覆盖，可重试/恢复，不假称空档 |
| 云离线/冲突（适用时） | 不用空档覆盖远端，不回退较新进度 |
| schema未知或玩法转换 | 原始档保留，有明确转换/恢复路径，不能静默reset |
| 升级后的正常继续玩 | 新产生进度能正常保存，旧资产仍可使用 |

对资源、最高纪录等不能简单要求“字节完全不变”；应按经过审查的字段转换和不减损断言验证，旧数据的备份指纹与迁移结果都留证。包含真实账号/存档的证据仅保存在受控本地忽略目录，不打印或提交；可复用fixture必须脱敏、有版本和结构来源。

## 工具与发布记录

工具箱的存档升级回归入口将旧构建和候选构建置于**同一测试origin、同一浏览器context**，先用旧版UI或明确标记的脱敏fixture建立记录，再切换候选并重复启动。两个不同localhost端口或直接给新版本灌一份数据，不足以证明自然升级。浏览器测试仅覆盖已声明的本地存储与场景，平台/云端与iOS WebView要在对应环境补验。

```sh
npm run qa:save -- \
  --project /absolute/path/to/game \
  --engine webkit \
  --old-dir /absolute/path/to/published-build \
  --new-dir /absolute/path/to/candidate-build \
  --scenario /absolute/path/to/game/scripts/save-upgrade-scenario.mjs \
  --out /absolute/path/to/game/output/save-upgrade/unique-run
```

场景导出 `metadata`、`seedOld({page})`、`assertUpgraded({page,before})`、`assertReload({page,before,reloadIndex})`。`metadata.seedKind` 明确 `OLD_UI` 或 `SANITIZED_FIXTURE`；脱敏fixture还需 `fixtureVersion`，`storageTypes` 明确 `localStorage` / `indexedDB`。每阶段针对 `progress / resources / unlocks / records` 返回 `name / storage / category / expected / actual`，比较方式为 `equal / at-least / includes`；每个声明的storage在每阶段都要有直接读回的断言，不适用类别需明确理由。runner计算结果，不仅接受场景自报 `passed:true`。旧档基线仅驻留内存，报告对键/数据库/store/检查标签/fixture版本/异常消息都只保存哈希及必要数量、类别和结果，不导出明文资源、账号和数据库内容。

回归入口拒绝生产URL、外部HTTP/WebSocket和清库，旧/新构建树在前后核对哈希，默认重复加载候选两次以抓重复发奖/消耗。普通JSON兼容的IndexedDB数据可以做结构指纹；未声明的数据库、无法读取或不支持的值类型不能标通过。旧版某种存储非空，候选或重载后该种存储整体为空，会独立判失败，不能靠另一种存储的正常值蒙混；当前不支持跨storage整体搬迁的自动放行，需要另建明确映射与专门测试。`SAVE_UPGRADE_PASS` 只覆盖本次场景与存储，`releaseGate` 仍为 `NOT_EVALUATED`。场景是受信本地代码，必须审查断言是否来自旧版基线而不是新版本自己给出的默认值；指纹存在本身不证明数据库中每项权益被保留。

本次工具验证：60项Python管理/隔离检查、10项JS存档测试通过，覆盖正常迁移、错误重置必须失败、重复迁移发奖必须失败、IndexedDB消失/未断言拦截、指纹和错误/标签明文隐私。默认CI没有游戏Playwright时只跑接口规则，浏览器项明确skip；本机完整命令为 `MOBILE_QA_PLAYWRIGHT_PROJECT=/absolute/game npm run qa:check`。这些测试不等于已修复11款历史数据。

`--engine chromium|webkit` 分别运行现有引擎，默认Chromium。相同10项测试已在两个引擎通过；用 `MOBILE_QA_BROWSER_ENGINE=webkit` 选择WebKit集成回归。WebKit是本机已有运行时，本次未下载Xcode或新浏览器；WebKit结果不等于iOS原生验收。

另对鉴宝两个实际正式归档 **0.14.1→0.14.3** 做了两引擎的代表性回归：从旧bundle初始状态建立明确标记的脱敏fixture，包含银两/累计收益、局数/层数、藏品/升级/道具、最好成绩、图鉴和回执；旧包重载确认后切候选，读取实际游戏状态，升级及两次重载四类权益保持，旧/新版号与构建哈希核对通过。结果为 `SAVE_UPGRADE_PASS`，仍是 `releaseGate=NOT_EVALUATED`；不代表真实玩家全量数据、其他历史版本、其他十款游戏或TapTap原生容器已验收。细节保存在忽略的 `output/mobile-qa/treasure-formal-save-upgrade-1793199176/`，不提交合成存档内容或包体。

每个发行记录保留旧/新commit与ZIP哈希、实际存储key/DB/namespace/schema、fixture来源、迁移链、字段断言、异常恢复、重复启动与适用平台结果。该轮汇总 `saveCompatibility=PASS / FAIL / UNKNOWN`；任一适用路径失败或未测均阻止本任务提审、上线和更新宣传。验收报告不得用“存档继续可用”代替字段核对证据。

历史已经丢失的数据未必能由新迁移自动找回。先只读寻找旧key、备份、旧来源、平台云记录和玩家自愿导出；没有可恢复来源时准确记录，不能凭空恢复、伪造补偿或宣称已找回。

2026-10-28源码只读抽查已发现真实风险：部分库读取/解析异常后回退新档并允许写回，部分旧玩法换key只发固定补偿，严格schema/内容ID过滤和历史列表裁剪也可能使旧记录不可见。当前没有全局清库的统一证据，不能把所有丢档归给 `clear()`。新港和鉴宝已有读失败保护/备份测试可作实现参考；其他库必须补各自保护和历史fixture后，才能将本项门禁标通过。风险定位在忽略的 `output/mobile-qa/save-compatibility-audit-20261028.md`，不将只读审查冒充已经修复或找回玩家存档。
